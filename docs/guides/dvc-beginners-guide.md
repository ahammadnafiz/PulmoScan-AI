# DVC for Beginners: End-to-End Practical Guide

If you are new to **Data Version Control (DVC)**, this guide will help you understand its purpose, key concepts, and exact workflows. You will learn how Git and DVC work together to make machine learning projects fully reproducible without bloating your repository.

---

## 1. What is DVC and Why Do We Need It?

Git is excellent for tracking plain-text code files, but it behaves poorly with large binary files (such as 2 GB datasets, `.pt` PyTorch weights, or `.h5` model files). If you track these heavy files in Git:

1. Your repository size grows exponentially.
2. Pulling and cloning the repo becomes extremely slow.
3. Git's diff system cannot track changes inside a binary file anyway (it only sees that the entire file changed).

**DVC acts as "Git for Data and Models."** It lets you keep your large files in a separate dedicated storage unit (like Google Drive, AWS S3, local folders, or Azure Blob) while keeping tiny text-based "pointer" files in Git.

```
                  ┌─────────────────────────────────────┐
                  │          Your Local Repo            │
                  │                                     │
                  │  ┌────────────┐     ┌────────────┐  │
                  │  │ main.py    │     │ model.pt   │  │
                  │  │ (python)   │     │ (150 MB)   │  │
                  │  └─────┬──────┘     └─────┬──────┘  │
                  └────────┼──────────────────┼─────────┘
                           │                  │
                           ▼                  ▼
                  ┌────────────────┐  ┌────────────────┐
                  │    Git Repo    │  │   DVC Remote   │
                  │ (GitHub/GitLab)│  │ (S3/GDrive/etc)│
                  │ tracks code &  │  │ stores heavy   │
                  │  tiny pointer  │  │raw binary bytes│
                  └────────────────┘  └────────────────┘
```

## 2. Core Concepts of DVC

To understand DVC, you only need to learn three concepts:

### A. Data Tracking & Pointer Files

When you ask DVC to track a file (e.g., `model.pt`), DVC:

1. Moves the actual file into its local cache directory (`.dvc/cache`).
2. Creates a tiny text file named `model.pt.dvc`. This file contains a unique **content hash** (MD5) representing the data.
3. Automatically adds `model.pt` to your `.gitignore` so Git never commits it.
4. **You commit the tiny `model.pt.dvc` file to Git.** Anyone who clones your repo can use DVC to read that pointer file and download the exact matching model.

### B. Remote Storage (DVC Remotes)

A **Remote** is the external drive or cloud bucket where DVC backups your data. When you run `dvc push`, DVC copies the heavy files from your local cache up to this remote. When you run `dvc pull`, DVC downloads them back.

### C. Pipelines & Directed Acyclic Graphs (DAGs)

Instead of running individual python files manually (`python stage1.py`, `python stage2.py`), DVC lets you define your training stages in a single `dvc.yaml` file. 

- **Dependencies (`deps`):** Files the stage needs to run (e.g. data or code).
- **Parameters (`params`):** Hyperparameters defined in a `params.yaml` file.
- **Outputs (`outs`):** Files generated by the stage (e.g. model weights).
DVC reads this file, builds a dependency graph, and manages execution automatically.

## 3. Step-by-Step Hands-On Workflow

Here is how you use DVC in your everyday work, using **PulmoScan AI** as the practical example.

### Step 1: Getting Started as a Collaborator (`dvc pull`)

If you clone the project repository for the first time, you will notice that the `Data/` folder and `models/` checkpoints are missing (because they are gitignored). 

To fetch them instantly from our Google Drive remote:

```bash
# 1. Activate your virtual environment
source venv/bin/activate

# 2. Pull all heavy datasets and models
dvc pull
```

DVC reads the `dvc.lock` file, matches the hashes, downloads the binaries, and restores them in their exact paths on your computer.

---

### Step 2: Running the Pipeline (`dvc repro`)

The entire training sequence is configured in `dvc.yaml`. You do not need to run separate stages manually. Simply run:

```bash
dvc repro
```

#### Why is this highly efficient? (Pipeline Caching)

DVC checks the content hashes of your code, configurations, and input data:

- If **nothing** has changed since the last run, DVC displays:
  ```
  Stage 'data_ingestion' is cached - skipping run.
  Stage 'prepare_base_model' is cached - skipping run.
  Stage 'training' is cached - skipping run.
  Stage 'evaluation' is cached - skipping run.
  ```
  It finishes in under a second by skipping unnecessary work!
- If you edit `params.yaml` to change the `LEARNING_RATE`, DVC is smart: it knows `data_ingestion` and `prepare_base_model` are unaffected. It **skips** those first two stages, and only runs the `training` and `evaluation` stages.

---

### Step 3: Visualizing the Pipeline (`dvc dag`)

To see how the stages are connected and how data flows through the project, run:

```bash
dvc dag
```

This prints a clean ASCII diagram showing the execution order:

```
                  +----------------+  
                  | data_ingestion |  
                  +--------+-------+  
                           |          
                           v          
                 +--------------------+
                 | prepare_base_model |
                 +---------+----------+
                           |          
                           v          
                     +----------+     
                     | training |     
                     +----+-----+     
                           |          
                           v          
                    +------------+    
                    | evaluation |    
                    +------------+    
```

---

### Step 4: Tracking and Comparing Metrics

During evaluation, the pipeline saves accuracy and loss metrics to `scores.json`. DVC knows this is a metrics file. You can query your scores directly from the CLI:

```bash
dvc metrics show
```

If you make changes to your hyperparameters and want to see if your accuracy improved compared to your last Git commit, run:

```bash
dvc metrics diff
```

DVC will parse the JSON structures and output a clean table showing the exact gain or loss in accuracy across git commits.

---

### Step 5: Backing Up Your Work (`dvc push`)

If you make changes—for example, you add new images to the dataset or train a better model checkpoint—and want to share your changes with the team:

1. **Run the pipeline to generate the new model:**
  ```bash
    dvc repro
  ```
2. **Upload the heavy binaries to the remote store:**
  ```bash
    dvc push
  ```
3. **Commit and push the updated pointer files (`dvc.lock`) to Git:**
  ```bash
    git add dvc.lock scores.json
    git commit -m "feat: retrain model with new hyperparameters"
    git push
  ```

## 4. How to Set Up DVC in a New Project (From Scratch)

If you want to start a brand new project using DVC:

1. **Initialize Git and DVC in your project directory:**
  ```bash
    git init
    # Install DVC
    pip install dvc
    # Initialize DVC
    dvc init
  ```
2. **Add a local backup folder (simplest remote setup for learning):**
  ```bash
    # Create a backup folder outside your project
    mkdir -p /Users/username/dvc_backup

    # Configure it as the default DVC remote
    dvc remote add -d myremote /Users/username/dvc_backup
  ```
3. **Start tracking a file:**
  ```bash
    # Tell DVC to track a large file
    dvc add dataset.zip

    # Commit the changes to Git
    git add dataset.zip.dvc .gitignore
    git commit -m "add dataset tracking pointer"
  ```
4. **Push the data to your backup folder:**
  ```bash
    dvc push
  ```

## 5. DVC Command Cheat Sheet


| Command            | What it does                                               | When to use it                                            |
| ------------------ | ---------------------------------------------------------- | --------------------------------------------------------- |
| `dvc init`         | Initializes DVC in the current project directory.          | Once at the start of a brand new project.                 |
| `dvc pull`         | Downloads raw datasets and model files from the remote.    | Immediately after cloning a repo or pulling git branches. |
| `dvc push`         | Uploads raw datasets and model files to the remote backup. | After you successfully train a new model or update data.  |
| `dvc repro`        | Executes the pipeline DAG specified in `dvc.yaml`.         | Whenever you want to run or update your training cycle.   |
| `dvc status`       | Checks for changes between workspace files and DVC cache.  | To see if your local data files have changed.             |
| `dvc dag`          | Renders the pipeline's execution flow chart.               | To inspect the dependencies of your pipeline.             |
| `dvc metrics show` | Prints the logged metrics (e.g., `scores.json`).           | To quickly see the evaluation results.                    |
| `dvc metrics diff` | Compares metrics between different git commits/branches.   | To verify if a change improved model accuracy.            |
